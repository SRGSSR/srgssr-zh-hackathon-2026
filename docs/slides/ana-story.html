The rule is in gateway/communes.yaml, bound to the office’s key. Nothing in a request can change it. If Public AI times out (we saw 504s under load), the gateway moves on to a Swiss host within the rule.

The rule is checked three times

  1. Once per request

    Rejects anything that tries to steer routing: client fallbacks, tags in body, metadata or header, api_base, a deployment id as model, spoofed metadata, a key without a rule.

  2. Before every attempt

    First try, retries, fallbacks. Keeps only deployments whose jurisdiction the rule allows, in the rule’s order. Missing metadata is excluded (fail closed).

  3. Right before each send

    Re-checks the deployment and the exact URL about to be used.

The queue lives in the gateway

  • No allowed service up: the request waits, in Switzerland.
  • A job is visible only to the key that submitted it.
  • Its text is deleted as soon as the job ends.
  • A waiting job survives a gateway restart.

Consent is not a request parameter

  • Only a rule with consent_can_add accepts it. Social services refuse it.
  • Given in a dialog, recorded, valid for one request.
  • Swiss and EU services are still tried first.

What we found in the Utility’s setup

  • Fallbacks cross borders and model families. Every Apertus group falls back to SEA-LION (Singapore) and Bielik (Poland). We ran their config against test hosts: with both Apertus 70B hosts down, a normal request was answered by the Singapore one.
  • Not every Apertus host has a stated country. Apertus 70B runs at Infomaniak (CH) and Featherless (country not stated); the 8B models run only at Featherless.
  • The Public AI API doesn’t say who served a request. It routes to “inference partners worldwide”, and no response header names the partner. Issues #33 and #35 on their repo ask for exactly this.
  • Tag routing can’t enforce “Switzerland only”. Retries and fallbacks widen the tag set; litellm_metadata.tags in the body sent 10 of 10 requests to the US deployment; a deployment id as model skips the filter (tested on v1.92.0).
  • Jurisdiction metadata can’t reach LiteLLM today. The Helm template keeps only two cost fields of model_info and drops the rest. Our upstream/ patch fixes that.
  • TLS verification is off (ssl_verify: false), so nothing binds a provider name to the real server. We saw why it matters: a stale DNS cache sent one demo request to another container while every log named the right one. Only the counters caught it.

Details and evidence in docs/findings.md.

What we don’t claim, and what’s next

We can’t prove

  • Where a provider physically computes. That needs contracts, audits or attestation.
  • What the Public AI API does internally with its inference partners.
  • That consent is legally enough. That is for each office’s data protection officer.

Out of scope

  • A compromised gateway host or a malicious operator.
  • The shared online demo runs on AWS in Frankfurt (EU). A real gateway runs in the commune’s environment in Switzerland.
  • Network egress controls. In production they back the policy.
  • The gateway and its logs are in the data path; events carry routing data only.

Next

  • Upstream the metadata and the policy to the Utility.
  • Turn TLS verification on; add evidence per provider.
  • Move the queue from one SQLite replica to a shared store for autoscaling.

Model-agnostic: the layer works with any model. Apertus makes the whole chain open.
